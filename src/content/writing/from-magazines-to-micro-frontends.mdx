A design review, a founder asking why you picked these tools, and a frontend interview are the same conversation. Someone wants to know why the app is built this way. They also want to know what you would refuse to add.

I used to prepare for that by drilling React trivia. Trivia helps you write components. It does not help you choose an architecture. Architecture here means how the pieces are arranged, and what you give up for that arrangement.

Three choices are worth being able to explain. One is why the product stays open as a single app, instead of loading a new page each time. Another is why you would skip Next.js, a React framework that can also build the page on the server. The third is when a backend for frontend stops helping. That is a small server that reshapes data for one kind of screen. It becomes a problem when that server can take the whole screen down with it.

If you can walk through those choices, you can be trusted with the system. If you can't, you can still ship the screens.

This is how the web got to those choices. Each way of building it answered a real pain, and each one added a new pain. The last section is a checklist for the repo you have now.

## The web was a magazine

Before frontend was a job, the web was a document.

Tim Berners-Lee's bet was linked documents, which he called hypertext. You requested a URL, the address of a page. The server sent HTML, the markup for that page. The browser painted it. Another page meant another request.

JavaScript, which lets a page respond to you, shipped in 1995. CSS, which controls how the page looks, became a standard in 1996. The deal did not change. A click still loaded a whole new page.

This fits when the product is something people read, such as docs, a marketing site, or this blog on a good day. The page had one job: show the words and the pictures before the reader got bored.

Anyone with a browser could read you, and that was the benefit. The cost was that reading was the whole product. A form could post to the server. The server would think, and a new page would come back. The screen did not remember you between those loads.

People wanted the page to know who they were. A file on disk cannot do that.

## The server started building the page

The next step was a way to build a fresh page on each request.

The name is model-view-controller, usually shortened to MVC. Trygve Reenskaug sketched it in 1979 for Smalltalk, a programming environment at Xerox. He wanted to separate what is true from what you are looking at. About 20 years later, web frameworks borrowed the names. Django, Ruby on Rails, ASP.NET, and the PHP frameworks all shipped the same split.

The browser stayed thin. A thin client mostly shows a page the server has already built. A controller took the request. A model talked to the database. A view mixed that data into HTML. The person got a page that had never existed as a saved file.

A logged-in visitor could see their name. A cart could remember a quantity. You could run real logic without asking the browser to hold the product.

<WritingFigure
  src="mvc"
  alt="Model-view-controller. A controller with validateEmail, hashPassword, and getUserList points at an HTML and CSS view, and at a user model with id, email, name, and a database."
  caption="The server builds the page. The browser only displays it."
/>

The gain is a page that can differ per person. The request stays in one language. A new teammate can hold the model in their head.

The cost shows up on every click. The browser loads a full new page. The frontend and the backend ship together, so they stay tied. Moving from Rails to Django is not a stylesheet change. It is a rewrite of the product.

In 2004, building HTML on the server was an acceptable cost. More visitors meant more of that work on your machines. You also did not need a frontend specialist yet. There was barely a frontend.

I have shipped this shape without calling it MVC. If the server paints the whole page and the browser only displays it, you are in that family. It is still a sound choice for many admin tools and internal apps. Nobody is pretending those are products you linger in.

A full reload is fine for a document. It is a poor fit for a tool you stay inside.

## The app moved into the browser

Gmail launched in 2004 and updated the inbox without loading a new page. A year later, that style got the name Ajax. Ajax means the page asks the server for new data and stays where it is.

The libraries that treated the browser as the home of the app came later. AngularJS came first, React followed in 2013, and Vue followed in 2014. The page stopped reloading. One JavaScript app stayed open and changed the screen in place. That pattern is a single-page application, or SPA. The important change was where the logic lived. It left the server and sat in the browser.

The server stopped sending a finished page. It started sending data through an API, a way for the browser to ask for what it needs. That data was usually JSON, which is text rather than HTML. On the server, the remaining work shrank toward storage and permission checks. Login, input checks, which screen you are on, and the memory of the session moved into the bundle. The bundle is the JavaScript file the browser has to download before the app can run.

The web could finally feel like a desktop program. Think of a dashboard, an editor, or a canvas you stay inside, instead of a page you visit and leave.

That is when the frontend job became real. HTML had not become harder. There was finally enough logic in the browser that someone had to own it.

<WritingFigure
  src="spa"
  alt="A single-page app using React, Vue, and Angular keeps client state, routing, and logic, and exchanges data with a REST API in front of a user model and controller."
  caption="The app runs in the browser and asks an API for data."
/>

An SPA can grow in ways a server-built page could not. You can put the files on a CDN. A CDN is a set of servers that keep copies of those files near the reader. A larger team can work on the interface, because the interface is now its own product. You can also keep memory that should not flash white on every click, such as a canvas, a spreadsheet, or a gym logger.

Two problems came with that move, and they still come up when someone asks how the app is built.

The first is a blank first screen. The browser has to download the bundle, read it, and run it before it can show anything real. People stare at an empty page. A crawler, the program a search engine uses to read your site, may see nothing. That is an SEO problem. SEO, search engine optimization, is whether a search engine can read the page and show it.

The second problem is how much the browser now decides.

<Callout tone="note" title="Thin clients and thick clients">
A thin client asks the server to decide, then shows the result. A thick client keeps the business rules, the state, and often the login. It treats the backend more like a database you call over the network.

Neither is a moral choice. The question is how much logic belongs in the browser. That code is slow to download, anyone can change it, and it is hard to keep in sync with the server.
</Callout>

<WritingFigure
  src="thin-vs-thick"
  alt="A thin client, shown as a classic web page that keeps state, routing, and logic on the server, and a thick client using React, React Router, and Redux that keeps them in the browser. Both call the same REST API, model, and controller."
  caption="A thin client follows the server. A thick client decides for itself."
/>

GW Infra is the first full product I would still show someone. It is a site for a solar company. React talks to Express, a Node.js server. The login is a signed token stored in the browser, called a JWT. The admin panel is more of the same client. That was the right call. Nobody needed Google to index the CMS, the screens for editing the site's content. The interaction was the product. A thread around then said SPAs were finished. Starting this one in Next.js would have solved a problem I did not have.

Teams moved logic into the browser because they wanted richer products. Phones then made that bundle slow to open, so some of the logic started moving back to the server.

## One API could not fit every screen

An SPA fed the wish for interaction on a desktop. Then the same company shipped phones.

Now there was a website, an iPhone app, an Android app, and maybe a TV app. All of them asked one backend for the user, shaped for that screen. A general API starts out helpful. Over time it becomes a compromise nobody likes.

That API is usually REST. REST means a URL returns a fixed shape of data, one thing at a time. The phone cannot afford the extra fields the desktop sidebar wants. The website wants a different mix than the app. You send too much, you send too little, or you invent an endpoint named `/api/v3/home-screen-but-for-tablet`.

One API for every experience is the part that stops working. A backend per experience is the replacement. The web team owns the web one. The iOS team owns the iOS one, unless iOS and Android are truly the same experience.

The name is backend for frontend, shortened to BFF. Nick Fisher coined it at SoundCloud, and Phil Calçado wrote the pattern up in 2015. [Sam Newman](https://samnewman.io/patterns/architectural/bff/) wrote the longer article people still pass around. Stewart Gleadow's line, which Newman recommends, is "one experience, one BFF."

Each BFF sits inside your network. It calls the services behind it and returns the shape that screen needs. Login can happen once. The encrypted connection, HTTPS, can happen once. The mix of data is decided next to the screen. A team that never sees the screen is the wrong place for that mix.

<WritingFigure
  src="bff"
  alt="A web single-page app and a mobile app each talk to their own backend-for-frontend. Those backends handle auth, aggregation, and pagination, then call shared users, products, and payments microservices."
  caption="Web and mobile each get a backend shaped for that screen."
/>

This is why a BFF comes up even if you have never shipped one. It is often the service closest to your screen. Netflix used a version of this so the Android app could change its API without waiting on one contract for every client.

The costs are the part people skip on the whiteboard.

You added a service on the path, so a request can take longer. You can also replace several calls from the browser with one call, and that can make the screen faster. At SoundCloud, moving the profile assembly into the BFF made that screen cheaper for the client. The speed depends on which calls you remove.

You also added a piece that can fall over and take one whole app with it. The services behind it can be healthy, and the website or the phone app still looks down. That is a single point of failure. One piece dies, and that app dies with it.

You also tied the BFF tightly to one interface. That is the point, and it has a price. If two products slowly become different, a shared BFF starts to hurt. If they stay the same, two BFFs are wasted work.

The gain that matters is the team. People who own users, catalog, and orders can ship on their own schedule. The frontend is not stuck waiting on one resource that tries to please every screen. The upfront cost is more infrastructure, and a frontend person who has to think about services.

Swasya made this concrete for me. Nurses had a mobile app, written with Flutter, a toolkit for phone apps. Doctors had a React dashboard. Those two screens were never going to want the same response. If I had pushed both through one REST API, each app would have kept reshaping the data on its own. I wanted shared services underneath, and a different mix in the server closest to each screen. That is a BFF, even when the folder is only called `api/`.

### GraphQL lets the screen ask for less

A BFF builds the shape on the server, once per experience. GraphQL lets the screen describe the shape itself.

The client asks for the fields it needs, and only those fields. Facebook had been doing this inside the company since the iOS News Feed work around 2012. They open-sourced it as [GraphQL](https://engineering.fb.com/2015/09/14/core-infra/graphql-a-data-query-language/) in 2015.

REST sends too much when `/users/1` returns 20 fields and a small badge needed 2. REST sends too little when a profile needs the user, then their posts, then each post's author. You pay for that with a chain of requests. Behind a GraphQL server, you can still hide many services. The frontend can change a screen without waiting on a new URL. The backend can keep shipping its own services.

The new work sits on the server. The functions that load each piece of a query are called resolvers. When resolvers call each other, a wasteful pattern becomes normal. You fetch a list of posts. Then you fetch the author once per post. That is the N+1 problem: one query, plus one more for every row.

[DataLoader](https://github.com/facebook/DataLoader) is the usual fix in JavaScript. It groups those lookups into one batch for the current request, and it remembers them until that request ends. The batching idea is older than the library. Facebook had a similar tool in 2010, and the JavaScript version shipped with GraphQL.

GraphQL moves the cost onto the server. The tools help if you watch how many database calls one screen triggers.

<Callout tone="warning" title="Two screens are not a GraphQL problem">
GraphQL fits clients that need many shapes of the same data.

If you have two screens and a stable REST API, you do not need it. You would be adding a query language to avoid writing two endpoints.
</Callout>

You can get the data shape right and still show people a blank screen.

## Send real HTML on the first response

A BFF and GraphQL changed the data. They did not shorten the wait before someone sees something useful.

<WritingFigure
  src="javascript-weight"
  alt="A page-load timeline from a blank frame to a finished page. Markers include first byte, first paint, first contentful paint, largest contentful paint, and time to interactive, including the gap between when the page looks usable and when a tap works."
  caption="A heavy page stays blank, then can look ready before a tap works."
/>

Teams took the interface model they liked in the browser and ran it on the server again. React, Vue, and Svelte describe a page as a tree of parts, and that same tree can be built on a server. Next.js does this for React. Nuxt does it for Vue. People call these meta-frameworks. A meta-framework wraps React, Vue, or Svelte, and it chooses the URLs, the data loading, and where the page is built.

Three names get used as if they were one choice. They are not.

**Static site generation (SSG)** builds the HTML ahead of time. You save the file, put it on a CDN, and serve that same file to every visitor. It arrives quickly because the file already exists, and it is cheap to serve. You cannot change the page per person. You cannot change a heading without a rebuild. This essay is that kind of page.

<WritingFigure
  src="ssg"
  alt="Static generation. The browser requests a route from a CDN of prebuilt pages. A Next.js or Nuxt build pipeline writes the HTML and CSS from a database or content store."
  caption="The page is built once, then served as a file."
/>

**Incremental static regeneration (ISR)** is that saved page with a timer. Next.js made the pattern popular. After a time limit, the next visitor still gets the saved page. A fresh copy is built in the background. A later visitor gets the new page. Content can change without a full deploy. You still do not have a live session. You have a page that updates on a delay.

<WritingFigure
  src="isr"
  alt="Incremental regeneration. The browser gets a saved page from a CDN. After the page passes its time limit, the next visitor still receives the saved page, and a Next.js or Nuxt server rebuilds the HTML in the background."
  caption="The saved page stays up while a fresh copy is built."
/>

**Server-side rendering (SSR)** runs the framework on each request. The visitor gets real HTML, with real data, in the first response. Crawlers can read it. People see a page instead of a spinner. The server has to do that work during the visit. A slow or personal query delays the moment anything arrives.

<WritingFigure
  src="ssr"
  alt="Server rendering. The browser requests a route from a Next.js or Nuxt server, which pre-renders the page and injects initial state from a database or content store. The browser then rehydrates that page so it can be used."
  caption="The server builds a fresh page for every visit."
/>

Sending HTML on the first response creates the next gap. The page can be visible before it works.

## You can see the page before you can use it

Hydration is the step that connects the two halves. The server sent HTML so you would see something. The browser still has to download the JavaScript and start the framework. Then it attaches clicks, and the app's memory, to HTML that is already on screen. Until that finishes, the buttons look ready. They do not work yet. That gap is why "we render on the server" leaves out the second half.

<WritingFigure
  src="hydration"
  alt="Hydration sequence. A server sends CSS, HTML, and JavaScript. The browser renders the HTML and reaches first contentful paint, then downloads, parses, and executes the bundle, hydrates the server HTML, and only then becomes interactive."
  caption="You see the page first. It accepts clicks after JavaScript loads."
/>

The server can go further. It can keep the parts that never needed to be a program. A product description, a footer, or this article can stay on the server, and their JavaScript is never sent. React calls those parts React Server Components. The browser only receives the pieces that click, type, or listen for updates.

The Next.js App Router, its current way of organizing pages, treats server components as the default. You can ship much less JavaScript. You can also lose a week drawing lines between server and browser that you did not mean to draw. `'use client'` is the marker that forces a part to run in the browser.

<WritingFigure
  src="rsc"
  alt="React Server Components. Next.js pre-renders the page, injects initial state, and drops JavaScript for server-only components. The browser rehydrates a smaller tree made of the interactive nodes, not the whole server tree."
  caption="Only the parts you can click are sent as JavaScript."
/>

Some frameworks start from the other end. The page is plain HTML, and you add JavaScript only where a region has to be alive. Those regions are called islands. Katie Sylor-Miller named the pattern. [Jason Miller wrote it down](https://jasonformat.com/islands-architecture/). Astro made it the default. A blog with one search box should not download the code for a whole dashboard.

React Server Components start from a React tree and leave the quiet parts on the server. Islands start from a document and add the live parts. You can land in a similar place. The default you start from is different.

This site mixes them on purpose. The writing is content, so it wants HTML. The gym logger is a product, so it wants a client. On Astriq, a product I built, most of the page stays in React Server Components. The parts that have to be alive are client islands. What matters is that rendering choice, and the reason for it.

There is a real cost. For a public page, the goal is to show the words in the first response and send little JavaScript. This is the option that does that. It costs more to run than a SPA on a CDN. It is harder for a new teammate to learn. It ties you more tightly to one framework. You need servers, rules for how long a saved page stays fresh, and people who understand those rules. Search gets better. The cheap path, copying files to a CDN and skipping the server, gets harder to keep.

I keep a private list of teams that adopted Next.js because it was the popular default, then moved off it. [Railway](https://dev.to/sarah-railway/moving-railways-frontend-off-nextjs-2hg5) is a public example. Their client-heavy product left Next.js after production builds passed 10 minutes, about 6 of them inside Next.js. The dashboard and the canvas were not using the server-rendering features. Other products have gone back to a plain SPA, using a client bundler such as Vite. A logged-in dashboard does not need Google to index the settings page. Server rendering before you have that problem is a choice made for a constraint you do not have.

<Callout tone="warning" title="Pay for the server only when you need it">
A SPA on a CDN is still a serious choice when the problem is somewhere else. The first screen, search, and a different page per person are the problems that call for the server.

A meta-framework is a bill. You pay it in servers, builds, and concepts the team has to hold.
</Callout>

A faster first screen does not make the codebase smaller.

## One app needs walls when the team grows

I have not worked on a client with 300 people. I have worked on frontends that started tidy and ended as a long `components/` folder with no labels. Past a certain size, the question becomes how people stop breaking one another's work.

The practical middle is a modular frontend monolith. You still ship one application. You draw boundaries inside it. A platform group owns the shared pieces: the design system, login, loading data, logging, and analytics. Other groups own parts of the product, such as users, payments, and catalog. The folders are named after those parts. I wrote about the folder version of this in [The Shape of a Codebase](/about/writing/the-shape-of-a-codebase). The architecture version is the same idea, with more at stake.

<WritingFigure
  src="modular-monolith"
  alt="A modular frontend monolith. Billing, products, payments, and users are separate domains. Under them, shared UI and logic covers the design system, global CSS, hooks, and validation, and shared services cover auth, data fetching, logging, and analytics."
  caption="One app, with each part of the product in its own box."
/>

Older architecture books show up here. Teams often keep using them after they stop helping.

**Clean Architecture** says code dependencies should point inward. [Robert C. Martin wrote the version people cite in 2012](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html). At the center are the stable nouns of the business: User, Order, Cart. Around them are the use cases, the actions the product can take. Frameworks, the database, and the interface sit on the outside. In theory, you could swap React for Vue and the center would not notice.

<WritingFigure
  src="clean-architecture"
  alt="The Clean Architecture as concentric circles. Entities sit in the center, then use cases, then controllers, gateways, and presenters, then devices, the web, UI, a database, and external interfaces. Arrows point inward. Beside the circles, control flows from a controller through a use case interactor to a presenter."
  caption="Business rules stay in the center, away from the framework."
/>

**Hexagonal architecture** is the same idea with a different drawing. Alistair Cockburn described ports and adapters in 2005. The application sits in the middle. It talks to the outside only through ports, the allowed ways in and out. A screen, an HTTP API, and a test harness are adapters plugged into those ports. Jeffrey Palermo's onion architecture, from 2008, draws the same idea as rings. The center is the business rules. The database sits in an outer ring.

<WritingFigure
  src="hexagonal"
  alt="Hexagonal architecture. Entities are the center. Interactors and a transport layer face HTTP and a queue. Repositories and data sources face a database, a gRPC API, and a REST API."
  caption="The app sits in the middle. Everything else plugs in around it."
/>

I like these drawings as a way to think. I would not use them as the default layout of a frontend.

Most interface frameworks already tell you where things go. Next.js will tell you where a page goes. A lot of what people call business logic in a React app is what the button does. That code belongs next to the button. I have almost never seen the later payoff from swapping the framework. If the product will live 15 years, and might survive a rewrite of the view, the separation can earn its keep. If it is a 2-year product with 8 screens, the extra layers will sit unused.

<Callout tone="idea" title="When the extra layers earn their keep">
I would reach for this on a long-lived product area, a thick client, or tests that must run without rendering React. I would also reach for it if the view might be replaced.

Otherwise I keep the actions close to the screens, and I let the framework be the framework. Separating layers is a skill. Not every file has to demonstrate it.
</Callout>

A modular monolith has costs even without those drawings. Data that every area can change starts to leak across the lines you drew. People have to keep respecting the lines, or the lines fade. CI, the automated build and test run, gets slow because you still build the whole app. You can draw the areas on a whiteboard and still import payments from catalog "only this once."

The split is only as real as the habit that protects it. A lint rule can do that job too. A lint rule is a script that rejects a bad import before it merges.

A folder boundary is sometimes not enough.

## Split the deploy when teams cannot wait

Micro frontends are for when a boundary inside one repo is not enough. The company also has to be large enough to pay for separate deploys.

[Cam Jackson's article](https://martinfowler.com/articles/micro-frontends.html) still has the clearest definition. They are frontend apps that can ship on their own, then get joined into one product. ThoughtWorks, a software consultancy, listed the term in 2016 as something worth a serious look. The visitor still sees one site. The header might be one app, the catalog another, and checkout a third. A shell is the outer app that stays on the page. It owns the shared CSS, which section you are in, and maybe the login. The other apps load inside it.

Module Federation, import maps, single-spa, iframes, and assembling the pieces on the server are all ways to load those apps into one page. The separate deploy is the decision that matters. Which loader you pick matters less.

<WritingMermaid
  title="One page, several applications"
  caption="Each slice owns its screen, and often the backend for that screen. If the shell gets complicated, you have one app with extra deploys."
>

```
flowchart TB
    visitor(["Visitor"])
    shell["App shell<br/>routing, session, shared CSS"]
    headerMfe["Header"]
    catalogMfe["Catalog"]
    checkoutMfe["Checkout"]
    accountMfe["Account"]

    visitor --> shell
    shell --> headerMfe
    shell --> catalogMfe
    shell --> checkoutMfe
    shell --> accountMfe
```

</WritingMermaid>

This follows Conway's Law. Conway's Law says a system ends up shaped like the way the teams who build it talk to each other. Teams that release separately tend to end up with frontends that deploy separately. Teams that share one pipeline wait on each other.

At a company with hundreds of engineers on one client, you need this, or something that behaves like it. A team of 8 can spend 6 months on the wiring and tell themselves they got faster.

The costs are hard to miss once you list them. Dependencies get copied, unless you are strict about what is shared. The page gets slower, because it is several bundles joined while it loads. One part of the page can run a newer library than another. That mismatch is called version skew. The design system has to work as an agreement between teams who do not sit together. Running it starts to look like backend microservices. Those are many small services, each shipped on its own. A deploy is no longer one action. "We shipped" can mean half the page shipped.

I would not add micro frontends to a side project to make the architecture look advanced. I would still be ready to talk about them. Companies that do not need them still ask, the same way people ask about Kubernetes for a to-do app. Kubernetes is a system for running many services. The useful part of the answer is the situation that calls for it. You want several teams on different release schedules. The product can no longer ship as one build. You also need room in the budget for the extra cost.

<Callout tone="note" title="Name the blocked team first">
If you cannot name the team that is stuck on the shared pipeline, you do not have a micro frontend problem.

You are collecting architectures before you have the pain.
</Callout>

## A map you can point at

Every style above is still running somewhere. The web kept the older options when SPAs arrived, and stacked new ones on top. A serious product often uses two or three at once. The marketing site can be saved HTML. A product page that changes per person can be built on the server. The signed-in app can be an SPA. A BFF can sit in front of three services. The repo can stay one app, split into areas, while someone is already talking about separating the deploys.

If you are one team, with one website, you can often stop at an SPA or at pages built on the server. The later rows are for pains you can already point at.

| Style | You get | You pay |
| --- | --- | --- |
| Static / SSG | A fast start, low cost, less to operate | Content that goes stale, and no per-person page |
| MVC | Logic on the server, one deploy | A full reload on every click, and a frontend tied to the backend |
| SPA | Interaction, files served near the reader, a rich product | A blank first screen, weaker search, a large download |
| BFF | Data shaped for one client, teams shipping in parallel | Another service that can take that client down |
| GraphQL | Each screen asking for its own fields | Server work, and one lookup that turns into one per row |
| SSR / RSC | Content on the first screen, better search, less JavaScript in the browser | Servers, more concepts, a tighter tie to the framework |
| Modular monolith | Many people, still one deploy | Boundaries that fade, and a slow build |
| Micro frontends | Separate deploys at a large company | A slower page, more operations, more coordination |

If you need the choice on one diagram, start from the pain in front of you. Team size, the first screen, and the shape of the data are different pains. The fix for one of them will not fix the other two.

</WritingMermaid>

## Check your own app

Do this on the repo you are shipping this week.

Open the project and write the answers down. If they stay in your head, they stay fuzzy.

1. **What style are you in?** SPA, SSG, SSR, BFF, modular monolith, or some stack of those. "We use React" is not a style. "We use Next.js" is barely one.
2. **Why did you land here?** Search, a phone client, a team that doubled, or a tutorial someone liked. A real reason beats a polished one.
3. **Where is the client thick, and where is it thin?** If checks on input live only in the browser, that is a security hole waiting. If the server draws everything and the client does nothing, that is a product hole waiting.
4. **What is the next step that fits the pain?** If the build takes 20 minutes and four teams share one pipeline, stricter modules come before separate deploys. If people leave because the first screen is slow, the next step is rendering, not a split deploy.
5. **What would you refuse?** A BFF for a single web client. GraphQL for two endpoints. Clean Architecture for a marketing page. Next.js for a logged-in tool that already has a Go API.

After that, "we use React and Next.js" is no longer the answer. You can say something like this.

> The marketing pages are static HTML. Product pages that differ per person are built on the server. The signed-in app stays in the browser, with a small BFF in front of the services that own the data. The repo is still one app, split into areas. If the team doubled, I would make those boundaries stricter before I split the deploys.

That paragraph is the proof you can see the system. A "we went with someone more experienced" is often this gap, phrased politely.

I still get this wrong. I have reached for a server because the surrounding conversation was loud. I have also shipped an SPA, then been surprised that a shared link did not look like a finished page. The checklist is how you catch that.

Before you name the architecture, write down the last constraint that forced a change.

If you can only explain the folders, you know the tools. If you can explain that constraint, you know the product.
</Callout>
