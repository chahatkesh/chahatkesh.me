You open a repo to add a coupon at checkout. The folders either lead you to that coupon, or they send you through five directories for one behavior.

The form has to accept the code. A rule has to reject a bad one. A request has to save it. A test has to prove the reject. When those files live apart, the coupon has no address.

Folders are not the whole architecture. Architecture here also means who may import whom, who owns the data, and which choice is expensive to undo. A tidy tree can still hide a mess of imports.

You still meet the folders on every change. They decide what sits together. They decide which boundary you can cross without noticing.

Four shapes show up in real repos. They are not a ladder. A small internal tool can stay on the first one for years. The block below is the same store, drawn four ways.

Open `src/` and count to five. If you still can't say what the product does, the folders are naming the framework.
</Callout>

## Group files by what they are

This is **layered architecture**, and it is where most repos begin. The folder name is the kind of file. Components sit with components. Hooks sit with hooks. Requests sit with requests.

A tutorial can teach that sort in a minute. A button is a component, so it goes in `components/`. A date helper goes in `utils/`.

The layout fits when the change is technical too. A new button style does touch many components. A header on every request does belong in one client.

A coupon is a different kind of change. The form goes in `components/`. The state goes in `hooks/`. The request goes in `services/`. The types go in `types/`. The test may live in a fifth folder.

Each of those files has a home. The coupon does not.

The cost shows up as the product grows. `components/` gets too big to scan. `utils/` fills with code no one owns. A change that should stay local becomes a walk through the repo.

I would leave a prototype in this shape. I would leave a small internal tool here too, if the work stays technical. I would leave this shape once the product's features have names. Those names are the next shape.

## Name the product at the top

**Screaming Architecture** is Robert C. Martin's name for that test. He [wrote it down in September 2011](https://blog.cleancoder.com/uncle-bob/2011/09/30/Screaming-Architecture.html). Look at the top of the tree and say what the system is. If you can't, the folders are talking about the tools.

A house plan reads as a house before anyone names the bricks. A store's top folders should be `catalog`, `cart`, `checkout`, and `orders`. They should not be `components`, `hooks`, and `services`.

Next.js still claims a top folder. The App Router, its current way of organizing pages, calls that folder `app/`. You can't rename it. The miss is when the rest of the top is framework names too.

Hide `app/` and look again. `catalog` and `checkout` mean the tree is about the product. A remainder of `components/` and `hooks/` means it is about React.

A name starts a boundary. It does not prove the boundary holds. `checkout/` might be a module with a public file. It might be the same unsorted files, under a product word.

I would not rename a young prototype every time the noun shifts. `workspace` on Monday and `team` on Friday is churn. Wait until the same word shows up in two tickets.

Then use that word as the folder. If the ticket says workspace, `tenant-management/` makes every change start with a translation.

<Callout tone="note" title="Use the word on the ticket">
A folder people have to translate is a folder they will skip. If the ticket says workspace, the folder should say `workspace`.
</Callout>

The top of the tree can now say checkout. The files inside it can still be scattered by kind.

## Keep one behavior in one folder

**Vertical slice architecture** is how you stop that scatter. [Jimmy Bogard](https://www.jimmybogard.com/vertical-slice-architecture/) aimed it at layers. A stack of folders is a layer. A diagram of circles around a core is still a layer. Both group code by technical role.

A slice groups one request instead. On a server, the request might be applying a coupon. On a frontend, the folder lesson is the same. `apply-coupon` holds the screen, the check, the request, and the test.

A search page that only reads should not grow an empty service file to match a diagram.

Bogard couples along the change. Files you touch in one task should sit together. A slice should not import another slice's private files.

The coupon now has an address. Open `apply-coupon/`. You can see how far a change spreads. Deleting the behavior is close to deleting the folder.

The cost is repeated code. Two slices may each format a price in a few lines. Deleting every repeat on sight looks tidy. It also ties together features that need to change on different days. A local copy stays visible. Pull it out when a second slice changes for the same reason.

He names a second limit. This layout assumes you can tell when a slice has grown a real business rule. If you can't, every slice stays a short script, and that rule never gets one home.

The slices still have to talk. Checkout needs the cart total. Add-to-cart needs to know if the product is in stock. Importing a private file for that keeps the folders vertical and the dependencies crossed.

Each slice should export one public file. Callers use that file. A function, a query, or an event is enough.

I would not slice a compiler, or a pipeline of transforms. Those changes follow the pipeline, so layers can stay honest. Slices fit when the task is a piece of the product.

One folder per behavior holds until two people would file the same code in two slices.

## Add a rule when people disagree

The strict version is **Feature-Sliced Design**, usually shortened to FSD. It is the strict frontend version of this idea. Layers come first, then slices, then segments such as `ui`, `model`, and `api`. The segment says what the file is for.

The figure shows six layers: `app`, `pages`, `widgets`, `features`, `entities`, and `shared`. The [spec](https://feature-sliced.design/docs/reference/layers) lists a seventh, `processes`, and tells you not to add it. A flow across pages belongs in `features` or in `app`. The figure leaves `processes` out.

Those six are not a checklist. [Version 2.1, from November 2024](https://github.com/feature-sliced/documentation/releases/tag/v2.1), says to start on the page. Keep the coupon's form, request, and state there until a second page needs them. `app` and `shared` are not split into slices. The layers between them are.

A generic helper can move to `shared` once a second caller exists. Product behavior can move to `features` or `entities` once a second page uses it. An entity folder for a type that only one page uses is a folder you don't need yet.

The part that stays strict is the import direction. A layer may import from a lower layer. It may not import from a higher one. A page may use the cart entity. The cart entity may not import the checkout page.

Neighboring slices stay apart too. Two entities may refer to each other only through an explicit cross-import, usually a folder named `@x`. The exception is visible in the path. Any other import of a neighbor breaks the rule.

Each slice publishes one file, usually `index.ts`. Code outside `features/checkout` imports that file. It does not open `features/checkout/model` for a private value. The inside can change without a review from the whole app.

Use this when several people need the same answer about a new file. "Use your judgment" has already produced five trees. The cost is ceremony. Six layers, and a public file on every slice, can outweigh a three-screen product.

[Steiger](https://github.com/feature-sliced/steiger), the linter from the FSD project, can mark a slice that only one page uses. That mark means move the code back onto the page.

I would not copy the full layer set onto a weekend project. I would not copy it for a team of one, either. I would add the import rule once two features reach into each other's private files.

The names still don't reject a bad import. Something else has to.

## A folder does not stop an import

I learned this by moving files into `features/` and stopping there.

The sidebar looked split. A caller could still import a private path, such as `features/checkout/model/coupon`. The folders had changed. The dependencies had not.

If a boundary matters, breaking it has to be harder than keeping it. A public `index.ts` will not do that alone. Callers can ignore the file.

Write a few rules while the coupon is still the example:

- who may import whom
- what `apply-coupon` exports
- where a shared price formatter may live
- which layer may call the network
- how checkout may read the cart total

A lint rule can fail the bad import before review. A package can expose only its public file, so other code can't import the private ones. Pick the lightest option that fails the build. The failure belongs in CI, the automated build and test run.

If you can't name one import that should fail, you don't have a boundary yet. You have folders.

<Callout tone="warning" title="Name the import that should fail">
If every file may import every other file, the next bad import will get through. The folder will not stop it. Write down the import that should fail the build.
</Callout>

## Match the folders to the next change

I don't keep one of the four forever. I match the shape to the change in front of me. I also match it to how many people have to make it.

**A prototype needs the next file to be findable.** Empty `widgets/` and `entities/` folders don't help you find it.

**Feature-sized tasks want slices.** A pipeline of transforms wants layers.

**A review should not be a surprise.** More editors means more value in a public file, and in a lint rule that fails.

**A campaign page needs fewer rules than billing.** Hoping you might need the structure later is a weak reason. A mess you have paid for twice, a hiring plan, or a dated roadmap is stronger.

**Shared code needs a second caller.** Design tokens, login, and logging often deserve a stable folder. So does one HTTP client. HTTP is the protocol the browser uses to reach your server. A product behavior deserves one owner. Create `shared/` when a second feature already imports the file.

<Callout tone="idea" title="Add a folder for a pain you can point at">
Start with fewer folders. Name the product when the nouns stay still. Put one behavior in one folder when that behavior is the unit of work. Add the import rule when people file the same code in different places.
</Callout>

A small internal tool can stay layered for years. Several owners may need product names in the first month. An extra folder should remove a problem you can already point at.

| Shape | You get | You pay |
| --- | --- | --- |
| Layered | Files grouped by kind, and one home for a technical rule | A feature with no address |
| Screaming | Top folders that name the product | A good name on a folder that is still a pile |
| Vertical slice | One behavior in one folder | Copied helpers, and slices that import each other |
| FSD | A downward import rule, and a public file per slice | Empty layers, if you build the full diagram first |

## Move one feature, then stop

The week you are most annoyed is a bad week to move every file.

The diff is too big to review. The history of a line gets harder to follow, because the file moved. Shipping waits while people argue whether `user` is an entity or a feature.

Pick the feature that changes often and leaks. If that feature is the coupon, use the word already written on the ticket. Move only the files that are clearly part of it. Add the public entry. Send the next coupon change through that entry. Write the illegal import down the same day.

Don't create `shared/` first. Wait until a second feature wants the same file. If the two copies change for the same reason, move the smallest piece that is stable. If they only look alike this week, keep both.

The tree will be mixed. Leave it that way. The coupon follows the new rule. Older areas wait until a change there gets expensive. An even tree, built in one weekend, is time taken from the product.

## This site still splits a save

This site is a mix. One save shows the cost, and I keep the mix anyway.

Next.js requires routes to live under `app/`. The public gym page, the admin screens, and the API routes are there. An API route is the function that answers a request. The screens for logging a workout live together in `components/features/gym/`. The page file sets the title and renders the dashboard. It does not contain the save.

Saving a session starts in `workout-logger.tsx`. That file posts to `/api/gym`. The handler lives under `app/api`, and it uses helpers in `lib/`, including `lib/gym.ts`. The screen and the save are not in one folder.

I leave that split in place. Moving API routes out of `app/` would mean fighting Next.js for a shorter walk. The walk costs less.

A new screen starts inside its feature folder. A file moves to `components/shared/` or `components/ui/` only after a second feature imports it. A route file should place a screen on the page. It should not become the place where the behavior collects.

<Callout tone="note" title="A second import earns the move">
Keep a feature's screen, its types, and its tests in one folder. Move a file out only when another feature already imports it.
</Callout>

## Check the tree you have

Do this on the repo you will change this week. Use a real task, such as the coupon. Write the answers where someone else can read them.

1. **Name the starting folder.** "Somewhere in components" means the task has no home.
2. **Count the top-level folders it touches.** One means the behavior has an address. Five means you are walking.
3. **Name the owner.** Two teams in that folder will argue about it on every review.
4. **Name an import that should fail CI.** No name means the boundary is a label.
5. **Name one thing you will not add this month.** The full FSD layer set on a three-screen tool. A `shared/` folder with one caller. A repo-wide rename in the same week as the feature.

Before a new folder exists, write down the change it serves and who owns it. Write down the import that should fail.
